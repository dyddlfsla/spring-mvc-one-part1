



## 01. Web Application 이란?

웹 애플리케이션(Web Application)은 `네트워크를 통해 클라이언트와 서버가 통신하면서 기능을 제공하는 애플리케이션`이다.

사용자는 일반적으로 웹 브라우저와 같은 **클라이언트를 사용하여 서버에 요청을 보내고, 서버는 해당 요청을 처리한 뒤 그 결과를 클라이언트에게 응답한다.**

웹 애플리케이션에서 클라이언트와 서버 사이의 통신에는 일반적으로 HTTP(HyperText Transfer Protocol)가 사용된다.  

따라서 웹 애플리케이션의 가장 기본적인 동작 구조는 다음과 같이 이해할 수 있다.

클라이언트가 서버에 HTTP Request를 전송하고, 서버는 요청을 분석하여 필요한 작업을 수행한 후 HTTP Response를 클라이언트에게 반환한다.

서버가 수행하는 작업은 단순히 파일을 반환하는 것일 수도 있고, 프로그램의 비즈니스 로직을 실행하거나 데이터베이스를 조회하거나 다른 서버와 통신하는 작업일 수도 있다.

즉, 웹 애플리케이션은 단순히 웹 페이지를 전달하는 시스템이 아니라, HTTP 요청을 기반으로 프로그램이 실행되고 그 결과를 HTTP 응답으로 반환하는 애플리케이션이라고 볼 수 있다.

---

### ✅ 1. Client 와 Server

웹 애플리케이션은 기본적으로 `Client`와 `Server`의 관계를 기반으로 동작한다.

Client는 서비스를 요청하는 쪽이고 Server는 요청을 받아 처리하고 결과를 제공하는 쪽이다.

🚨 대표적인 Client에는 웹 브라우저가 있지만 반드시 브라우저만 Client가 되는 것은 아니다.

***모바일 애플리케이션, 다른 서버 프로그램, API 테스트 프로그램 등 HTTP 요청을 보낼 수 있는 프로그램이라면 모두 Client가 될 수 있다.***

Server는 Client가 전송한 요청을 받아 필요한 처리를 수행한다.

예를 들어 게시글 조회 요청을 받았다면 데이터베이스에서 게시글을 조회할 수 있고, 회원 가입 요청을 받았다면 전달받은 정보를 검증한 후 데이터베이스에 회원 정보를 저장할 수 있다.

따라서 Client와 Server의 관계를 단순하게 표현하면 다음과 같다.

<br>

> 💡 ***클라이언트는 필요한 작업을 요청하고 서버는 요청을 처리하여 결과를 반환한다.***

<br>

---

### ✅ 2. HTTP

HTTP(HyperText Transfer Protocol)는 클라이언트와 서버가 데이터를 주고받기 위해 사용하는 애플리케이션 계층의 통신 프로토콜이다.

프로토콜(Protocol)이란 `서로 다른 컴퓨터나 프로그램이 통신하기 위해 지켜야 하는 규칙`을 의미한다.

<br>

> 💡 ***Client와 Server가 서로 다른 프로그램으로 만들어져 있더라도 양쪽 모두 HTTP의 규칙을 따른다면 서로 데이터를 주고받을 수 있다.***

<br>

HTTP의 기본적인 통신 방식은 `Request`와 `Response`로 이루어진다.

클라이언트가 HTTP Request를 서버에 전송하면 Server는 해당 요청을 처리하고 HTTP Response를 반환한다.

즉 일반적인 HTTP 통신은 다음과 같은 흐름을 가진다.

```text
Client → HTTP Request → Server → HTTP Response → Client
```

HTTP에서 클라이언트가 먼저 요청을 보내고 서버가 그 요청에 대한 응답을 반환하는 것이 기본적인 구조이다.

```text
┌────────┐             HTTP              ┌────────┐
│ Client │ <---------------------------> │ Server │
└────────┘                               └────────┘
      \________ Internet / Network ________/
```

웹 어플리케이션은 기본적으로 HTTP 통신을 기반으로 동작한다.

***클라이언트에서 서버로 HTTP 요청을 보내면 서버는 요청을 처리하고 그에 맞는 HTTP 응답을 클라이언트에게 보내준다.***

---

#### 🟢 2-1. HTTP로 전달되는 데이터

HTTP는 처음에는 이름 그대로 HyperText 문서를 전달하기 위한 목적으로 만들어졌다.

초기 웹에서는 웹 서버가 HTML 문서를 제공하고 웹 브라우저가 이를 받아 화면에 표현하는 형태가 중심이었다.

하지만 HTTP 자체는 특정 데이터 형식만 전달하도록 제한되어 있지 않다.

그리고 발전을 거듭한 현재, HTTP를 사용하여 거의 모든 형태의 데이터를 전달할 수 있다.

대표적으로 다음과 같은 데이터를 전달한다.

- HTML
- 일반 Text
- CSS
- JavaScript
- JSON
- XML
- JPEG, PNG, WebP 등의 이미지
- 음성 데이터
- 영상 데이터
- PDF
- 각종 파일
- 기타 Binary Data

<br>

> 💡 **따라서 현대의 HTTP는 단순한 HTML 문서 전송 프로토콜을 넘어 다양한 시스템 사이에서 데이터를 주고받기 위한 범용적인 통신 프로토콜로 사용되고 있다.**

<br>

---

### ✅ 3. 웹 서버(Web Server)

웹 서버(Web Server)는 `HTTP 또는 HTTPS 통신을 기반으로 클라이언트의 요청을 받아 처리하는 서버 프로그램`이다.

웹 서버의 가장 기본적인 역할은 ***정적 리소스(Static Resource)를 제공하는 것이다.***

정적 리소스란 서버에 저장되어 있는 파일을 요청에 따라 **별도의 비즈니스 로직 처리 없이 그대로 반환하는 데이터**를 의미한다.

대표적인 정적 리소스에는 다음과 같은 것들이 있다.

- *.html
- *.css
- *.js
- *.jpg
- *.png
- *.gif
- *.mp3
- *.mp4

예를 들어 클라이언트가 이미지 파일을 요청하면 웹 서버는 서버에 저장되어 있는 해당 이미지 파일을 찾아 그대로 반환할 수 있다.

<br>

> **💡 정적 리소스는 요청할 때마다 프로그램 로직을 실행해서 새롭게 만들어지는 데이터가 아니라, 초기에 저장된 상태 그대로 제공되는 데이터다.**

<br>

---

#### 🟢 3-1. 웹 서버의 주요 역할

웹 서버는 단순히 정적 리소스만 제공하는 것은 아니다.

현대의 웹 서버는 다음과 같은 역할도 수행할 수 있다.

- 정적 리소스 제공
- HTTP 요청 수신 및 응답
- Reverse Proxy
- Load Balancing
- SSL/TLS 처리
- HTTPS 적용
- 캐싱
- 압축
- 접근 제어
- 요청 로그 기록

특히 실제 웹 서비스에서는 웹 서버가 클라이언트의 요청을 먼저 받은 뒤,  
동적인 처리가 필요한 요청을 뒤쪽의 웹 애플리케이션 서버로 전달하는 구조가 많이 사용된다.

---

#### 🟢 3-2. Reverse Proxy

웹 서버는 클라이언트의 요청을 직접 처리하지 않고 뒤쪽에 있는 애플리케이션 서버로 넘겨줄 수도 있다.

이러한 구조를 `Reverse Proxy`라고 한다.

예를 들어 다음과 같은 구조가 사용될 수 있다.

```text
Client → Web Server → Web Application Server
```

이 경우 웹 서버는 다음과 같이 역할을 나눌 수 있다.

- 이미지, CSS, JavaScript 같은 정적 리소스는 웹 서버가 직접 처리한다.
- 동적인 요청은 애플리케이션 서버로 전달한다.

이렇게 하면 정적 리소스 처리와 애플리케이션 로직 처리를 분리할 수 있다.

대표적인 웹 서버에는 다음과 같은 것들이 있다.

- **Nginx**
- **Apache HTTP Server**
- Microsoft IIS

이 중 Nginx와 Apache는 현재도 매우 널리 사용되는 대표적인 웹 서버이다.

---

### ✅ 4. 웹 애플리케이션 서버 (WAS, Web Application Server)

웹 애플리케이션 서버(WAS)는 웹 서버와 마찬가지로 ***HTTP 통신을 기반으로 클라이언트의 요청을 받아 처리할 수 있는 서버 소프트웨어다.***

웹 서버가 주로 정적 리소스를 제공하는 데 특화되어 있다면, WAS는 정적 리소스를 제공하는 기능뿐만 아니라 `프로그램 코드를 실행하여 동적인 애플리케이션 로직을 수행할 수 있다는 점`이 중요한 특징이다.

즉, 클라이언트의 요청에 따라 서버에 작성되어 있는 프로그램을 실행하고 그 결과를 동적으로 생성하여 응답할 수 있다.

예를 들어 다음과 같은 요청을 처리할 수 있다.

- 회원 정보 조회
- 로그인 처리
- 게시글 등록 및 조회
- 주문 처리
- 데이터베이스 조회 및 저장
- 외부 API 호출
- 사용자에 따라 서로 다른 결과 생성

<br>

> 💡 **웹 서버가 저장되어 있는 리소스를 전달하는 역할에 특화되어 있다면,  
> WAS는 요청에 따라 애플리케이션 코드를 실행하여 동적인 결과를 만들어내는 역할에 특화되어 있다.**

<br>

---

#### 🔴 4-1. 웹 서버와 웹 애플리케이션 서버와의 차이점.

기본적으로 웹 서버는 정적 리소스를 제공하는 서버이고, 웹 애플리케이션 서버는 애플리케이션의 비즈니스 로직을 수행할 수 있는 서버이다.

사실 둘의 경계가 모호하게 보일 수 있다.

웹 서버도 조금이나마 애플리케이션 로직 수행 기능이 있고 웹 애플리케이션 서버도 정적 리소스를 제공할 수 있기 때문이다.

그렇다면, 무엇으로 웹 서버와 웹 애플리케이션 서버를 구별할 수 있을까?

프로그래밍 언어마다 조금씩의 차이점은 있지만, ***자바에서는 서블릿 컨테이너를 제공하면 WAS 라고 한다.***

기본적인 역할을 기준으로 보면 다음과 같이 구분할 수 있다.

| 구분 | Web Server | WAS |
|---|---|---|
| 주요 목적 | 정적 리소스 제공 | 동적 애플리케이션 실행 |
| 정적 파일 제공 | 가능 | 가능 |
| 프로그램 로직 실행 | 제한적 | 가능 |
| 데이터베이스 연동 | 일반적인 주 역할이 아님 | 애플리케이션을 통해 가능 |
| 대표적인 제품 | Nginx, Apache HTTP Server | Tomcat, Jetty, Undertow 등 |

가장 단순하게 구분하면 다음과 같다.

정적 리소스를 제공하는데 특화된 것은 웹 서버, 애플리케이션의 로직 수행에 특화되어 있다면 웹 애플리케이션 서버이다.

---

#### 🟢 4-2. Java의 WAS와 Servlet Container

Java 웹 애플리케이션에서는 `**Servlet Container**`가 매우 중요한 역할을 한다.

Servlet Container는 Servlet의 생성, 실행, 요청 전달, 생명주기 관리 등을 담당하는 실행 환경이다.

Java 웹 애플리케이션에서 HTTP 요청이 들어오면 Servlet Container가 요청을 받아 적절한 Servlet에 전달하고, Servlet이 요청을 처리할 수 있도록 환경을 제공한다.

따라서 다음과 같은 Java 웹 기술은 Servlet Container를 기반으로 동작한다.

- Servlet
- JSP
- Spring MVC
- Servlet 기반 Spring Application

Spring MVC 역시 내부적으로 Servlet 기술을 사용하며, Spring MVC의 핵심인 `DispatcherServlet` 또한 Servlet이다.

따라서 Spring MVC 애플리케이션을 실행하려면 기본적으로 Servlet을 실행할 수 있는 환경이 필요하다.

대표적인 Servlet Container에는 다음과 같은 것들이 있다.

- Tomcat
- Jetty
- Undertow

국내 Java 웹 개발에서는 이러한 서버들을 일반적으로 **WAS라고 부르는 경우가 많다.**

> 💡 엄밀한 용어에서는 `Servlet Container`와 `Application Server`를 구분하기도 한다.
>
> Tomcat, Jetty 등은 기본적으로 Servlet을 실행하기 위한 Servlet Container의 성격이 강하고, Jakarta EE의 여러 기능을 종합적으로 제공하는 WebLogic, WildFly, Payara 등의 서버를 보다 엄밀한 의미의 Application Server라고 부르기도 한다.
>
> 하지만 일반적인 Java/Spring 웹 개발에서는 Tomcat을 WAS라고 표현하는 경우가 매우 흔하다.

---

### ✅ 5. 웹 시스템의 구성

앞서, 웹 서버와 웹 애플리케이션 서버를 알아보았다.

그렇다면 실무에서는 웹 서비스는 어떻게 구성되어 있을까?

#### 🟢 5-1. WAS + DB 로 구성하기

WAS 에는 정적 리소스 제공 기능이 이미 있기 때문에, 이론적으로는 WAS 와 DB 만으로도 웹 시스템을 구축할 수 있다.

```text
                          [애플리케이션 로직]
      ┌───────────┐       ┌────────────────┐       ┌───────────┐
      │  Client   │ ----> │     WAS        │ ----> │  Database │
      └───────────┘       └────────────────┘       └───────────┘
                           [HTML, CSS, js ]
                           [ *.jpg, *.mp3]
```

그런데, 이렇게 WAS 하나만으로 시스템을 구축하게 되면 WAS 가 너무 많은 역할을 담당하게 되어 서버 과부하의 우려가 있다.

또한 비용이 가장 큰 리소스는 애플리케이션 로직인데, 이 애플리케이션 로직이 상대적으로 저렴한 정적 리소스 때문에 지장 받을 수 있다.

또한 WAS 가 장애가 발생 했을 때, 안내 화면도 출력할 수 없다.

---

#### 🟢 5-2. Web server + WAS + DB 로 구성하기

그래서 대부분 시스템을 구성할 때 다음과 같은 구조로 설계한다.

```text
                                               [애플리케이션 로직]
      ┌──────────┐        ┌──────────────┐      ┌───────────┐       ┌───────────┐
      │  Client  │ ---->  │  Web server  │----> │    WAS    │ ----> │  Database │
      └──────────┘        └──────────────┘      └───────────┘       └───────────┘
                          [HTML, CSS, js ]
                          [ *.jpg, *.mp3]
```

실제 서비스에서는 Web Server와 WAS를 함께 사용하는 것이다.

클라이언트의 요청을 Web Server 가 먼저 받고, 요청의 종류에 따라 직접 처리하거나 WAS로 전달한다.

예를 들어, 정적 리소스는 Web Server가 직접 제공하고, 애플리케이션 로직 실행이 필요한 요청은 WAS로 전달할 수 있다.

이러한 구조에서 Web Server는 WAS 의 앞단에서 `Reverse Proxy` 역할을 수행할 수 있다.

웹 서버와 웹 애플리케이션 서버를 분리하면 다음과 같은 기능을 구성하기도 쉽다.

- 정적 리소스 처리
- Reverse Proxy
- HTTPS 처리
- Load Balancing
- 캐싱
- 여러 WAS로 요청 분산
